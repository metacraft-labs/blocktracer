# Gates that no CI job runs, with why each is still here. Not just ci/test/'s:
# the scan behind this register covers every test-shaped file in the tree.
#
# THIS FILE FAILS IN BOTH DIRECTIONS. A listed gate that stays dark is reported
# and does not fail the run. A listed gate that BECOMES REACHABLE fails the run,
# by name, demanding its line be deleted — so an entry cannot outlive the hole
# it records, and nobody has to remember to clean up after wiring one. A listed
# gate that no longer EXISTS fails too, so the register cannot accrue names that
# would one day silently excuse a file coming back.
#
# IT IS NOT AN EXEMPTION LIST. An entry does not say "this need not run". It
# says: this IS a gate, it SHOULD run, nothing runs it today, and here is what
# it would cost the person who wires it.
#
# ---------------------------------------------------------------------------
#
# ONLY ONE KIND OF DARKNESS BELONGS HERE.
#
#   LEGITIMATE — the gate cannot run because a capability it needs GENUINELY
#   DOES NOT EXIST yet. The entry must NAME that capability, in a
#   `MISSING CAPABILITY:` line, so the register says what would have to become
#   true for the line to be deleted. That turns each entry into a claim someone
#   can check and eventually discharge.
#
#   NOT LEGITIMATE — the gate could run and nobody wired it. That is not a dark
#   gate, it is an unwired one, and it does not land. Write the job.
#
# The distinction was written down here while this file was short rather than
# after it had fifteen entries, because a register whose bar is set once it is
# already long gets the bar its longest-serving entries deserve. The codetracer
# side has had three ceiling raises in a single day; this is the rule adopted
# there and it applies here identically.
#
# `MISSING CAPABILITY:` IS ENFORCED, not requested. `ci/test/ci-coverage.sh`
# fails on any entry whose preceding comment block does not carry one, and
# `ci-coverage-test.sh` plants an entry without one and requires that failure.
# A convention nobody checks is how the second kind of darkness gets in.
#
# Ported from codetracer's `ci/test/shell-gate-coverage.known-dark.txt`,
# including the rule that is the reason this file exists rather than two more
# workflow steps:
#
#     Wiring them is deliberately NOT done here. Each needs an owner who knows
#     what it costs to run, what it needs on the runner, and whether it passes
#     today — and a guard author quietly adding five unknown jobs to CI would be
#     making five decisions that are not theirs. What is done here is making the
#     number impossible to lose.
#
# Format: one REPO-RELATIVE PATH per line. `#` comments and blank lines ignored.
#
# Paths, not basenames, since 2026-09-04. The scan that feeds this register used
# to be `ci/test/` alone, so a basename was unambiguous; it now covers every
# test-shaped file in the tree, where two gates may share one. `ci-coverage.sh`
# says more about why the key changed rather than gaining a second form.

# ── the Noir DAP engine seam ────────────────────────────────────────────────
#
# Both landed on `dev` in the merge `d504a11` (from `56ce9c9`, "noir-dap:
# CodeTracer's Noir tests over the engine we ship, and the ten they find"),
# two days after `ci-coverage.sh` itself. Neither commit message mentions CI,
# a workflow, or a job; the merge's own scope statement is about a Justfile
# conflict. So the DARKNESS was an oversight — but wiring them is not the
# remedy, for a reason the commit states outright:
#
#     Ten checks are red and one request is never answered, so the lane exits
#     124.
#     Nothing is fixed here. Every finding is in the engine, which is a
#     published artifact from another repository.
#
# A gate that is RED BY DESIGN against today's engine, wired as an ordinary
# step, turns a truthful diagnostic into a permanently-failing job — and a job
# that is always red is a job everybody learns to ignore, which is how the
# `main` trigger rotted for 178 commits, arrived at from the other direction.
#
# WHAT IT WOULD COST WHOEVER WIRES IT, so the decision can be made by someone
# who owns it:
#
#   * `$CODETRACER_SRC` or a `../codetracer` sibling — available in `.#ci` from
#     the flake's pinned input, so this part is already paid for.
#   * `nim` and `node` on PATH — also `.#ci`.
#   * an 18 MB replay engine: `$REPLAY_ENGINE_DIR`, else
#     `client/dist/replay-engine`, else it FETCHES the published one. That is
#     the same unpinned artifact the `journeys` job takes from
#     `web-codetracer.pages.dev`, and it is the artifact every one of the ten
#     findings is about.
#   * NO SKIP PATH AND NO `--require` FLAG, unlike every other gate in this
#     directory. The script's header states the rule deliberately — "A suite
#     that goes green because its subject is absent is worse than no suite" —
#     so a runner missing an input gets a failure, not a skip. That is correct
#     for the gate and it is the reason it cannot be added defensively.
#
# MISSING CAPABILITY: a published wasm32 replay engine that answers the ten
# checks this lane makes — and answers the request it currently drops, which is
# what makes the lane exit 124 rather than merely go red. The engine is built
# and published by the `codetracer` repository; nothing in THIS repository can
# make the lane pass, which is precisely why it is dark rather than unwired.
# (The engine is fetched unpinned, so this can change without a commit here —
# the same property that retired the `journeys` Arm II refusal on 2026-09-04.)
#
# WHAT WOULD MAKE THIS ENTRY DELETABLE: that engine shipping. Re-run
# `just noir-engine-dap` against the published artefact; when the ten checks go
# green, wire the lane and delete this line — the guard above will demand it.
ci/test/noir-engine-dap.sh

# ── the Noir corpus's known-failure register ────────────────────────────────
#
# THE FIRST ENTRY HERE FROM OUTSIDE `ci/test/`, and it is here because it was
# never visible to be dark. Until 2026-09-04 `ci-coverage.sh` enumerated
# `ci/test/*.sh` and nothing else, so this file was not an uncovered gate — it
# was not a subject. ci.yml's own `deploy-gates` job had already written the
# same sentence about `tools/`: "not by `ci-coverage.sh`, whose enumeration
# reaches `ci/test/*.sh` and `client/Justfile` and nothing under `tools/`".
# The scan now covers every test-shaped file in the tree, and this is what that
# turned up.
#
# WHAT IT IS. 270 lines over `fixtures/trace/tour/manifest.json`: three
# toolchain programs pinned compile/error, and a both-directions known-failure
# register carrying NR-02, NR-03a and NR-04. Its rule is the one the journeys
# ledger states — a pinned defect that STOPS holding reports `NOW PASSING` and
# FAILS the run, so a fix cannot land without the entry recording it being
# deleted. `--selftest` drives both directions plus a base case. Its only
# callers today are `just corpus-check` and `just corpus-selftest`, and no
# workflow invokes either.
#
# IT PASSES. Measured 2026-09-04 on a workstation that has both binaries:
# "corpus: 3 pinned, 3 known failure(s) still open, 0 unexpected, 0 newly
# passing", exit 0. So this entry is NOT hiding a red — the gate is dark, not
# broken, and that distinction is why it was worth running before writing this.
#
# MISSING CAPABILITY: `nargo` and `ct-print` on a CI runner. Neither is a build
# dependency of this repository and neither can be produced by it. `nargo` is
# the Noir compiler, a 43 MB release binary built from the `noir` checkout;
# `ct-print` comes from `codetracer-trace-format-nim`. The script finds both by
# walking UP from its own directory into sibling checkouts — a workstation
# layout that does not exist on a runner — and `flake.nix`'s `ci` shell carries
# `nim nimble just python3 wrangler nodejs_22`, none of which is either one.
#
# WHAT IT WOULD COST WHOEVER WIRES IT, and why it is not being wired here:
#
#   * ABSENT `NARGO` THE SCRIPT EXITS 2 BEFORE MEASURING ANYTHING, and absent
#     `CT_PRINT` it counts the recording checks as `NOT RUN` and increments
#     `fail`. Both are deliberate — its header argues a register that quietly
#     checks nothing is worse than none — but both mean that adding this as an
#     ordinary step on a runner without the binaries buys a PERMANENTLY RED
#     job, which is the failure mode the two entries above are also about.
#   * So it needs a skip path that does not exist yet, and the shape is known:
#     skip LOUDLY, with skips counted separately from passes, so that "the
#     toolchain was absent" can never be read as "the corpus passed". Whoever
#     adds it must drive that branch in BOTH directions — present and absent —
#     because a skip path nobody has watched trigger is how a gate goes green
#     on an empty runner.
#   * Pinning where `nargo` comes from is a decision with a cost that is not a
#     guard author's to make: it is another repository's release artifact, and
#     the corpus's whole point is to pin what THAT toolchain currently does.
#
# WHAT WOULD MAKE THIS ENTRY DELETABLE: either binary set reaching a runner —
# a pinned `nargo` in the flake, or a published artifact the job can fetch.
# Then wire it with the counted-skip shape above and delete this line; the
# guard will demand it the moment the gate becomes reachable.
