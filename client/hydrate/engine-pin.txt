# engine-pin.txt — WHICH replay engine this repository fetches, by name AND by bytes.
#
# ── The defect this file closes ────────────────────────────────────────────
#
# `fetch-engine.sh` used to pull three fixed paths from the ROOT of the
# `web-codetracer` Cloudflare Pages project:
#
#     /worker.js
#     /pkg/db_backend.js
#     /pkg/db_backend_bg.wasm
#
# A Pages project's root always serves its CURRENT PRODUCTION DEPLOYMENT. So
# those three paths do not name an artefact; they name "whatever CodeTracer
# published most recently". Two agents fetching an hour apart on 2026-09-04
# legitimately received different engines — sha256 `e63dd40a…`/18,117,700 bytes
# and `22acb8e1…`/18,117,658 bytes — and neither was wrong, because nothing
# anywhere claimed they should agree. That cost two like-for-like comparisons.
#
# The script DID compute sha256s afterwards, but wrote them into a manifest as
# a RECORD of what this run downloaded. A record of drift is not a check
# against drift, which is why nobody noticed for as long as it existed.
#
# ── What is pinned, and how ────────────────────────────────────────────────
#
# `deploy-web-codetracer.yml` publishes each Noir Studio asset under
# `<name>.<first 16 hex of its sha256>.<ext>` with
# `cache-control: public, max-age=31536000, immutable`. Two of the three files
# this repository needs are in that set, so for them the URL IS the content: a
# fetch of `assets/db_backend_bg.842c7164dd667085.wasm` cannot return different
# BYTES under that name.
#
# ── It does NOT return 404 when the name is gone. Measured. ────────────────
#
# This file used to say the fetch "either returns those exact bytes or returns
# 404", and `fetch-engine.sh` was built on that sentence. It is false, and it
# is the reason deploy run 35041777226 was misread as CodeTracer's publisher
# being broken.
#
# Cloudflare Pages has no 404 for an unknown path: it serves the project's
# SPA fallback — the entry document — with status 200. Measured 2026-09-16
# against the live origin, a deleted asset and a name invented for the test
# answer identically:
#
#   assets/db_backend.f28f99e30356aebd.js          200  10514  text/html  (was pinned)
#   assets/db_backend_bg.22acb8e1ccf2d7aa.wasm     200  10514  text/html  (was pinned)
#   assets/definitely-not-a-real-asset.deadbeef.js 200  10514  text/html  (never existed)
#
# So a stale pin does not fail as a missing file. `curl -fsSL` SUCCEEDS, and
# without a check a 10 KB HTML document lands on disk named `db_backend.js`.
# A STATUS-CODE CHECK REPORTS A DELETED ASSET AS PRESENT — only the sha256
# below, and the content-type and doctype readings `fetch-engine.sh` now takes
# ahead of it, tell the difference.
#
# `worker.js` has NO content-addressed twin. `assets/replay-worker.<hash>.js`
# is a DIFFERENT file — the Studio's own host for the engine, written because
# it cannot use the engine's static `import "./pkg/db_backend.js"` — so it is
# not a hashed copy of `worker.js` and must not be substituted for one. Its
# URL therefore stays mutable, and the sha256 column below is the only thing
# holding it: a changed `worker.js` fails the fetch by name instead of being
# copied in silently.
#
# ── The cost, stated ───────────────────────────────────────────────────────
#
# An upstream engine release makes this file stale, and a stale pin FAILS the
# fetch — it does not fall back. That is the same cost the deploy workflow's
# engine step already accepts in writing ("an engine fix now needs a
# BlockTracer redeploy"), plus one reviewable commit. The remedy is one
# command and the diff is four numbers:
#
#     just engine-pin-update      # re-fetches from the project root, rewrites
#                                 # this file, prints the diff for review
#
# It is deliberately NOT automatic. A pin a script can update on its own is a
# pin that updates itself in CI, which is the unpinned state wearing a file.
#
# ── The follow-up this does NOT do, and why the obvious one is not it ──────
#
# Every CodeTracer release makes this file stale, and that recurring cost is
# real. The obvious answer — have `fetch-engine.sh` resolve the hashed names
# from the entry document at fetch time, the way `update-engine-pin.sh`
# already does — DOES NOT WORK, and it is worth writing down why so it is not
# re-proposed:
#
#   Resolving the NAME at fetch time still leaves the sha256 to assert. A
#   release changes the bytes, not just the name, so the resolved asset fails
#   the hash instead of failing the name. The pin goes stale at exactly the
#   same moment; only the message changes. And a resolve that did NOT assert
#   the hash is the unpinned state this file exists to end.
#
# The fragility is not in how the name is found. It is that the production
# alias serves only the CURRENT deployment, so yesterday's bytes stop being
# addressable at all. The fix that would actually work is to fetch from a
# PER-DEPLOYMENT origin, which Pages keeps alive across later releases — but
# that needs the deployment's own URL, and `deploy-web-codetracer.yml` does
# not publish one anywhere this repository can read. Measured 2026-09-16: the
# commit-hash guess is not it —
# `https://ed9aa650.web-codetracer.pages.dev/` is a Cloudflare 404, not a
# deployment alias. Getting one is a change in CODETRACER's workflow, not
# here, and it is not a reason to delay a re-pin.
#
# ── Format ─────────────────────────────────────────────────────────────────
#
# One record per line, whitespace separated, `#` comments and blank lines
# ignored. Plain text rather than JSON because `fetch-engine.sh` is bash and a
# bash JSON parser is a bug with a schema.
#
#   <dest-path>  <source-path>  <sha256>  <bytes>  <mutability>
#
#   dest-path    where the file is written under the destination directory.
#                This layout is the PUBLISHER'S and must not be flattened:
#                `worker.js` resolves `./pkg/db_backend.js` and the wasm
#                against `import.meta.url`.
#   source-path  what to fetch, relative to the base URL. Content-addressed
#                where one exists.
#   sha256       asserted after the fetch. Not recorded — asserted.
#   bytes        asserted after the fetch, and asserted AGAINST THE SOURCE for
#                the wasm: `ReplayEngineWasmBytes` in
#                `client/src/debugger/replay_engine.nim` must equal the wasm's
#                figure here, because that constant is rendered to a visitor.
#   mutability   `immutable` — the source-path is content-addressed, so the
#                origin cannot serve other bytes under it.
#                `mutable` — the source-path is a moving target and the sha256
#                is the only thing pinning it.
#
# ── THIS PIN IS LOAD-BEARING FOR THE PUBLISHED CORPUS. READ BEFORE BUMPING. ──
#
# Measured 2026-10-06 against live blocktracer.org. Bumping the wasm below to a
# CURRENT db-backend would refuse every container this site publishes — about
# 288,095 pages (163,539 `aztec`, 124,516 `aztec-testnet`, 37
# `aztec-testnet-frames`). The pages are static HTML and would still render; the
# INTERACTIVE REPLAY is what would go, everywhere, at once.
#
# Why, in one line each:
#
#   * the published containers are container version 3 with `meta.dat` SCHEMA 3
#     (sampled `aztec-testnet` container: 180,224 bytes, 94.5% zero, 5 Zstd
#     frames; re-measured end to end 2026-10-14, see the block below);
#   * THE ENGINE PINNED BELOW IS NOT OLD ENOUGH TO READ THEM. This bullet used
#     to say it was, and that it was "the ONLY reason replay works today".
#     Both halves are false and were measured false on 2026-10-14 — see
#     "THE PREMISE IS INVERTED" below. The pin is still load-bearing, but for
#     the opposite reason: it records WHICH too-new engine is deployed;
#   * a current db-backend's `meta.dat` set does NOT contain 3
#     (`db-backend/src/ctfs_trace_reader/meta_dat.rs`, `SUPPORTED_VERSIONS`).
#
#     CORRECTED 2026-10-14: this bullet used to name that set as {4,5,6} and the
#     container set as {2,3,4,5}. Both were stale within days, and the meta.dat
#     set has since been a SINGLE version twice over — `[6]` in the deployed
#     engine, and `&[META_DAT_VERSION]` with `META_DAT_VERSION = 7` at
#     `codetracer` `agents` today. The numbers were never the durable part, and
#     naming them here invited exactly the error that produced them: `[4,5,6]`
#     was read off a working tree 209 commits behind its own `agents` tip, and
#     an agent was briefed from it. THE DURABLE STATEMENT IS "NOT 3". Live
#     figures are measured per revision in the sections below, which are
#     maintained where this bullet was not — read those instead.
#

# the corpus and must not be bumped. The opposite is the case: the deployed
# engine is already two generations NEWER than the corpus, and interactive
# replay is therefore refused on every published page today. Every figure
# below was taken from bytes fetched over the network, not from a source
# reading or a transcription.
#

#   see the 2026-10-28 section. The reading is kept as what was true then.]

# WHAT THIS CHANGES. The old prescription — "do not bump the engine, it is the
# only thing keeping replay alive" — protects nothing, because the bump has
# already happened. The remedy is on the CORPUS side (re-record to container 5
# / `meta.dat` 6, which the deployed engine accepts today, or ship the compact
# profile) or else by deliberately pinning an engine that reads 3. Bumping the
# rows below toward `agents` would make it strictly worse: `codetracer`
# `agents` reads `meta.dat` {7}, and `codetracer-trace-format-nim` `agents`
# already WRITES 7, so a producer rebuilt from today's tips emits containers
# the CURRENTLY deployed engine also refuses — on the `meta.dat` axis, with the
# container axis still passing at 5, which is the quietest possible failure.
#
# The two axes are independent and that is the whole trap: the container gate
# was widened and the `meta.dat` gate was not, so "container v3 is accepted
# now" is true and insufficient. Widening the container gate alone was measured
# to change seven refusal MESSAGES and zero refusal OUTCOMES.
#
# WHAT TO DO ABOUT IT — and it is NOT "migrate the corpus to the newest full
# format". That was this note's first prescription and it was wrong; corrected
# 2026-10-07 on the owner's direction.
#
# The published recordings are NOT to be re-recorded into a newer version of the
# FULL profile. They are expected to be superseded by the COMPACT profile, which
# all recordings are likely to end up using. So the transition is one step and
# not three, and the two halves move TOGETHER:
#
#   * the producer emits compact archives (`CCP-6`), and
#   * the engine below gains the compact loader (`CCP-5` landed it in the
#      db-backend; the pinned wasm does not carry it — measured: zero hits for
#      every compact-specific string in it, against a positive control that
#      finds the version and magic messages, and a negative control).
#
# Neither half is useful alone. Shipping compact archives to this engine breaks
# them; shipping this engine a compact loader does nothing while the corpus is
# full-profile v3. That is the real coupling, and it is a smaller one than a
# version migration: the corpus is REPLACED, not converted.
#
# So the only rule this file needs to carry is the safety one:
#
#   DO NOT BUMP THE WASM BELOW ON ITS OWN. Bump it together with the publish
#   that replaces the corpus, or not at all.
#
