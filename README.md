# BlockTracer

A static block explorer produced by an ingest / process / publish pipeline, where
every transaction can carry a full time-travel debugging trace generated by
CodeTracer's recorders. The browser reads **static files and nothing else** — no
API, no database, no per-request compute.

See the specs in `codetracer-specs/BlockTracer/` for the full design and the
`BlockTracer.milestones.org` plan.

## Status

This repository currently implements the **demo-first decoupling seam** — the first
slice of the plan:

- **M5b — Data Contract.** The versioned contract between the chain-extractor and
  the site-generator, encoded as concrete Nim types plus a conformance validator.
- **M5c — Demo Data Generator.** A fake extractor/trace-gen that emits a valid,
  Aztec-shaped static tree honouring the contract, so the front end, publishing and
  the visual-design campaign can be built against demo data before real ingestion
  (M6) or real replay (M10) exist.

Everything else in the plan — the IsoNim explorer UI, browser replay, the
publisher, real ingestion — is a later milestone and is **not** built here. See
`docs/data-contract.md` for exactly what is and is not in scope.

## Layout

```
src/blocktracer/contract/     the data contract: version, ids, typed model
src/blocktracer/validator.nim the conformance validator (both producers run it)
src/blocktracer/demo/         the Demo Data Generator
src/blocktracer_demo_gen.nim  CLI: emit a demo tree
src/blocktracer_validate.nim  CLI: validate a tree against the contract
tests/tcontract.nim           conformance, determinism, cross-producer, negatives
fixtures/trace/               a STAND-IN .ct container (see its README)
docs/data-contract.md         the contract representation and why
```

## Build and run

No third-party dependencies — the Nim standard library only.

```sh
# run the test suite
nimble test

# generate a demo tree and validate it
nimble demo

# or directly:
nim c -r src/blocktracer_demo_gen.nim --out:demo-site
nim c -r src/blocktracer_validate.nim demo-site
```

The demo generator is **deterministic**: the same `--seed` produces a
byte-identical tree (containers included), so its output is a usable regression
fixture.

## The contract in one paragraph

There is a single `ContractVersion`, carried by `root.json` (`contractVersion`) and
by every trace `manifest.json` (`schema`). A transaction is stored as immutable
`TransactionFacts` (discriminated unions for identity, ordering, outcome, roles,
cost and code edges), with generation-scoped state, a versioned `TraceSelection`
overlay and code interpretation kept in **separate** layers that change on
different cadences. A trace's URL is *derived* from the immutable facts plus the
registry's recorder pin, so the client (and the validator) locate every `/t/…`
artifact with no lookup. An Aztec transaction's private part is structurally
unobservable, so it is represented as `availability: absent` **with a reason** —
never a failed fetch — while its public part carries a trace.
